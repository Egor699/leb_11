# Лабораторная работа №11

## 1. Суть `BlockingIOError`

`BlockingIOError` в Python соответствует низкоуровневым кодам `EWOULDBLOCK` / `EAGAIN`.

Это означает: **«операция сейчас невозможна без ожидания, но сокет работает в неблокирующем режиме»**.

Например, если новых подключений нет, `accept()` не ставит программу на паузу, а сразу возвращает ошибку. Ядро сообщает приложению: «очередь пуста, попробуй позже».

Это не сбой программы, а штатный сигнал о том, что данных пока нет.

## 2. Цена неблокирующего режима

Если убрать `time.sleep(0.01)`, сервер попадает в бесконечный «горячий цикл» — busy polling.

Программа постоянно вызывает `accept()`, хотя подключений нет. При каждом вызове происходит:

1. Переход из пользовательского режима Ring 3 в режим ядра Ring 0.
2. Проверка ядром очереди подключений.
3. Возврат ошибки `EAGAIN` / `EWOULDBLOCK`.
4. Возврат в Ring 3 и обработка исключения Python.

Поэтому загрузка ядра процессора достигает 100%, хотя полезной вычислительной работы программа не выполняет.

`time.sleep(0.01)` снижает нагрузку, так как во время паузы планировщик ОС отдаёт процессор другим задачам.

## 3. Альтернатива постоянному опросу

Промышленные серверы не опрашивают сокеты в бесконечном цикле. Они используют **мультиплексирование ввода-вывода**.

Сервер регистрирует сокеты в ядре и ждёт событий. Пока событий нет, поток спит и не расходует процессор.

Основные механизмы:

- **`epoll`** — Linux.
- **IOCP** — Windows.
- **`kqueue`** — macOS и BSD.

Когда появляется подключение или данные, ядро уведомляет сервер, какой именно сокет готов. Только после этого вызываются `accept()` или `recv()`.

Так работают nginx, Node.js и другие высоконагруженные серверы: они обрабатывают тысячи соединений без постоянной загрузки CPU.
